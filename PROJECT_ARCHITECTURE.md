### Folder rules

1. **`src/app/` contains routes only.** Every file in it becomes a screen/URL, so
   never put components, hooks, services or utils there. Route files stay thin:
   they import the screen from `src/domain/<feature>/screens/` and render it.
2. **There is no top-level `app/` folder.** Expo Router falls back to `./app` when
   `src/app` is missing, so a non-route `app/` folder at the root is a trap.
3. **Import through the alias:** `@/components/...`, `@/domain/...`,
   `@/assets/images/...` — no deep relative paths (`../../../`).

## Architecture Overview

### 1. **Store (Redux State Management)** ⭐ **CRITICAL**

The **store** is the centralized state management hub of the entire application.

**Key Components:**
- **rootReducer.ts**: Combines all domain-specific reducers (auth, chat, profile, vitals) into one global state
- **storeConfig.ts**: Initializes Redux store with middleware, dev tools, and persistence
- **hooks.ts**: Custom Redux hooks for type-safe dispatch and selector usage
- **persistConfig.ts**: Enables state persistence across app sessions

**Why Redux in the Store folder?**
```typescript
// ✅ GOOD: Centralized state management
const state = {
  auth: { isLoggedIn, user, token },
  chat: { messages, conversations },
  profile: { userData, settings },
  toast: { message, type },
  vitals: { data, history }
};

// All components can access state through one single source of truth
```

---

### 2. **Domain Folder (Feature-Based Architecture)**

Each domain represents a **feature module** with complete ownership of its business logic.

**Example: Auth Domain**
```
auth/
├── screens/              # UI Layer - What user sees
│   ├── LoginScreen.tsx
│   ├── RegisterScreen.tsx
│   └── ForgotPasswordScreen.tsx
│
├── components/           # Feature-specific components
│   ├── AuthLayout.tsx
│   └── EnvChangeModal.tsx
│
└── store/               # Redux for this feature
    ├── AuthReducer.ts   # State shape: { isLoggedIn, user, token }
    ├── actions/         # Sync actions
    ├── async-actions/   # API calls (thunks)
    └── services/        # API endpoints
        └── AuthServices.ts
```

**Why Domains?**
- ✅ **Modularity**: Each feature is self-contained
- ✅ **Scalability**: Easy to add new features without touching existing code
- ✅ **Team Collaboration**: Different teams can work on different domains
- ✅ **Code Reusability**: Screens, components, and logic stay organized

---

### 3. **Components Folder (Shared Components)**

Reusable UI components used across **all domains**.

**Examples:**
- `Toast/`: Global notification component
- `Loader/`: Loading indicator used everywhere
- `TextInput/`: Reusable input field with consistent styling
- `ScreenGuard/`: Security wrapper for sensitive screens
- `ButtonComponent/`: Standard button with app styling

**Why Shared Components?**
```typescript
// ✅ Instead of: Duplicating button code in auth, chat, profile
// ✅ Do this: Import ButtonComponent and reuse

import ButtonComponent from '@/components/ButtonComponent';

// Consistent styling across the app
// Easy to update all buttons in one place
```

---

### 4. **Navigation (Expo Router — `src/app/`)**

Navigation is file-based with **Expo Router**; there is no separate navigation
folder or `AppNavigator`. The folder structure under `src/app/` *is* the
navigation tree.

- **`_layout.tsx`**: Defines the navigator (Stack / Tabs) for its folder
- **Route groups `(name)/`**: Group screens under one navigator without adding a URL segment (e.g. `(auth)`, `(tabs)`)
- **Dynamic routes `[id].tsx`**: Screens with params, read via `useLocalSearchParams()`
- **Programmatic navigation**: `router.push('/chat/42')` or `<Link href="/profile" />` from `expo-router`
- **Typed routes** are enabled (`experiments.typedRoutes` in `app.json`), so invalid paths fail type-checking

```tsx
// src/app/(auth)/login.tsx — thin route file
export { default } from '@/domain/auth/screens/LoginScreen';
```

---

### 5. **Services Folder (Business Logic & APIs)**

Core application services that don't belong to a specific domain.

**Examples:**
- **NotificationService.ts**: Firebase Cloud Messaging integration
- **ScreenTracker.ts**: Tracks current screen for notifications
- **API Clients**: Service layer for backend communication

**Why Separate Services?**
- ✅ Can be used by multiple domains
- ✅ Easy to test and mock
- ✅ Separation of concerns

## Data Flow Architecture

```
User Interaction (Tap Button)
         ↓
   Component (Screen/UI)
         ↓
   Action → Dispatcher
         ↓
   Redux Middleware (async-actions)
         ↓
   API Call (NotificationService/AuthService)
         ↓
   Backend Response
         ↓
   Reducer (Updates State)
         ↓
   Selector (Components get new data)
         ↓
   Re-render UI
```

**Example: Login Flow**
```typescript
// 1. User taps login button
<ButtonComponent onPress={() => dispatch(loginUser(email, password))} />

// 2. Async action makes API call
export const loginUser = (email, password) => async (dispatch) => {
  const response = await AuthServices.login(email, password);
  dispatch(setLoginSuccess(response.token));
}

// 3. Reducer updates store
auth: { isLoggedIn: true, token: "jwt..." }

// 4. Component reads from store and navigates
const { isLoggedIn } = useSelector(state => state.auth);
useEffect(() => {
  if (isLoggedIn) router.replace('/(tabs)');
}, [isLoggedIn]);
```

## Why This Architecture is Better

### 1. **Modularity & Scalability**
- Each domain is independent
- Adding new features doesn't affect existing code
- Easy to maintain and debug

### 2. **Code Reusability**
- Shared components prevent duplication
- Services are used across domains
- Redux hooks are consistent everywhere

### 3. **Type Safety**
- Shared types and interfaces in `src/types`
- Redux hooks are fully typed
- Catch errors at compile time, not runtime

### 4. **Testability**
- Actions can be tested in isolation
- Reducers are pure functions
- Async-actions can be mocked

### 5. **Performance**
- Redux selectors prevent unnecessary re-renders
- State persists across app sessions
- Lazy loading of domain-specific code

### 6. **Team Collaboration**
- Clear folder structure
- Feature teams own their domains
- Minimal merge conflicts

## Best Practices in This Architecture

### ✅ DO
```typescript
// 1. Put domain-specific logic in /domain/[feature]/store
// 2. Use Redux for global state (auth, chat, etc.)
// 3. Use shared components from /components
// 4. Organize by feature, not by file type
// 5. Keep services in /services for cross-domain use
```

### ❌ DON'T
```typescript
// 1. Don't create state in component (use Redux instead)
// 2. Don't duplicate components (put in /components)
// 3. Don't put domain logic in root store
// 4. Don't mix feature screens with shared components
// 5. Don't make direct API calls from components
```

## Adding a New Feature

1. **Create domain folder**: `src/domain/newfeature`
2. **Add structure**:
   ```
   newfeature/
   ├── screens/
   ├── components/
   └── store/
       ├── NewFeatureReducer.ts
       ├── async-actions/
       └── services/
   ```
3. **Add to rootReducer.ts**:
   ```typescript
   import newFeatureReducer from '../domain/newfeature/store/NewFeatureReducer';
   
   export const rootReducer = combineReducers({
     auth: authReducer,
     newFeature: newFeatureReducer,
   });
   ```
4. **Add routes** as thin files in `src/app/` (e.g. `src/app/(tabs)/newfeature.tsx`) that re-export the screen from `src/domain/newfeature/screens/`
5. **Use shared components** from `/components`
